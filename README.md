# File Tagger

특정 디렉토리의 모든 파일/서브디렉토리를 읽어, 사용자가 정의한 **태그 및 태그값**을
파일·디렉토리에 부여하고, 그 태그를 기준으로 **정렬·필터·탐색**을 돕는 데스크톱
애플리케이션입니다.

## 주요 기능

**스캔 · 태그**

- 관리할 루트 디렉토리를 선택해 파일/폴더를 스캔하고, 폴더마다 관리 방식(폴더만 /
  내부 / 재귀)을 정해 인덱싱 범위를 조절
- 라벨 / 텍스트 / 숫자 / 날짜 / 링크 / 이미지 값 유형의 태그를 파일·폴더에 부여
- 파일 크기·수정 시각·이미지 해상도 등은 **시스템 태그**로 자동 부여되어 사용자
  태그와 똑같이 필터·정렬에 쓰임
- 파일을 옮기거나 이름을 바꿔도 태그를 따라 붙이는 이동 추적, 실시간 파일시스템 감시
- 외부 앱(브라우저 확장·다운로드 스크립트 등)이 파일을 저장하면서 태그까지 붙일 수 있는
  **태그 요청함**(아래 "외부 앱 연동" 참조)

**보기 · 탐색**

- 목록 / 아이콘 / 자세히 세 가지 보기 모드(모드마다 따로 기억되는 확대·축소)
- 태그 조합 **필터**, 태그값 기준 다단 **정렬**, 태그값·폴더 계층으로 묶는 **그룹**
  — 세 가지 모두 칩으로도, 자동완성이 붙는 텍스트로도 편집
- 분할 프리뷰, 썸네일, 키보드만으로 하는 목록 탐색·태그 수정

**커스텀 썸네일**

- "링크" 태그로 워크스페이스 안의 다른 항목을, "이미지" 태그로 바깥의 이미지 파일을
  노드 썸네일로 지정. 여러 태그를 우선순위 목록으로 두어 항목마다 맞는 출처를 고름

앱의 **도움말 보기**(F1)에 사용법·활용 팁·기능과 단축키·시스템 태그 설명을 모아 두었습니다.
도움말 메뉴에서 원하는 탭으로 바로 열 수 있습니다.

## 기술 스택

- **Flutter** (멀티플랫폼 GUI, 데스크톱 우선: Windows / Linux)
- **Drift** (SQLite) — 태그 영속화
- **Riverpod** — 상태 관리

## 태그 저장 방식

태그 데이터는 관리 대상 디렉토리 루트의 `.filetagger/` 폴더 안 SQLite DB에
저장됩니다. 폴더를 이동·복사하면 태그도 함께 따라갑니다. 앱 전역 설정(최근 연
폴더, 테마)만 태그 DB 바깥에 따로 보관하며, 그 위치는 배포 형태에 따라 다릅니다.

- **포터블판**(압축을 풀어 쓰는 형태): 실행 파일과 같은 폴더. 폴더째 옮기면 설정도
  함께 따라갑니다.
- **설치판**: 계정별 OS 애플리케이션 데이터 폴더.

같은 PC에서 두 형태를 함께 쓰면 설정이 서로 갈립니다(의도된 동작입니다). 또한
설정 파일을 쓸 수 없는 자리에서 실행하면 — 읽기 전용 매체에 둔 포터블판이나 권한이
없는 폴더 — 앱은 그대로 동작하되 **설정이 이번 실행 동안만 유지**되고, 상태표시줄에
"설정이 저장되지 않는 중"이 표시됩니다. 설정을 몰래 다른 위치에 대신 쓰지는 않습니다.

## 외부 앱 연동

### 태그 요청함

외부 앱이 **파일을 저장하면서 태그까지 붙이거나**, 이미 인덱싱된 파일의 태그를
추가·수정·제거하도록 하는 창구입니다. HTTP 서버나 플러그인 실행이 아니라 **약속된
폴더에 요청 파일을 넣어 두는 방식**이라, 앱이 켜져 있지 않아도 되고 외부 앱에 필요한
것은 "JSON 파일 하나를 쓸 수 있는 능력"뿐입니다. 요청함에 넣어 두면 앱이 다음에 그
폴더를 열 때(또는 켜져 있다면 곧바로) 처리하고 치웁니다.

#### 흐름

1. 외부 앱이 **파일을 관리 폴더 안에 먼저 저장**합니다.
2. `<관리 폴더>/.filetagger/queue/` 안에 **요청 파일**을 넣습니다. 파일 이름은 자유지만
   **확장자는 `.json`이어야** 합니다(그 확장자만 요청으로 읽습니다).
   **다 쓴 뒤에 `.json`이 되도록 rename하세요** — 예를 들어 `a1b2c3.json.tmp`로 쓰고
   `a1b2c3.json`으로 옮기면, 쓰는 중에 읽히는 일이 없습니다.
3. 앱은 **폴더를 열 때(스캔 직후)**, 그리고 **켜져 있는 동안 요청함이 바뀔 때마다**
   요청함을 읽어 적용합니다. 파일 추가와 태그 부여가 한 번에 성립하도록 스캔이 먼저 돕니다.
4. 성공한 항목은 **큐에서 빠지고**, 실패한 항목은 **그 자리에 남아 사유가 적힙니다**.
   파일에 담긴 항목이 모두 성공하면 파일째 지워집니다. 외부 앱은 자기가 만든 경로를
   그대로 다시 읽어 결과를 알 수 있습니다.

요청함 폴더(`queue`)는 관리 폴더를 열면 앱이 자동으로 만듭니다. `.json`이 아닌 파일은
요청으로 읽지 않으므로, 요청이 참조하는 이미지를 같은 폴더에 함께 둘 수 있습니다
(아래 `image` 참조). 그런 파일은 오래되면 실패 항목과 같은 기준으로 정리됩니다.

#### 한 파일에 여러 요청

최상위를 **배열**로 쓰면 한 파일에 요청을 여러 개 담을 수 있습니다. 결과 표기는
파일이 아니라 **항목 단위**입니다 — 성공한 항목만 빠지고, 실패한 항목은 제 사유를 단 채,
아직 처리되지 않은 항목은 그대로 남습니다. 모두 성공하면 파일이 지워집니다.

```json
[
  { "path": "신작/01.png", "tag": "읽음" },
  { "path": "신작/02.png", "tag": "작가", "value": "홍길동" }
]
```

**배열 파일은 한 번 써 놓고 덧붙이지 마세요.** 앱이 처리 결과를 반영하려고 파일을 다시
쓰므로, 그 사이에 덧붙이면 유실될 수 있습니다. 요청을 그때그때 밀어 넣는 외부 앱은
지금처럼 **항목당 파일 하나**를 쓰면 됩니다(두 형태를 같은 폴더에 섞어 써도 됩니다).

#### 요청 파일 형식

| 필드 | 필수 | 값 |
| --- | --- | --- |
| `path` | ✔ | 대상의 **관리 폴더 루트 기준 상대 경로**(`nodeType: keyword`면 키워드 **이름**) |
| `tag` | ✔ | 태그 **이름** |
| `op` | | `add`(기본) · `replace` · `remove` |
| `value` | | 태그값(문자열. 숫자·불리언으로 써도 문자열로 받습니다) |
| `missing` | | 그 이름의 태그가 없을 때: `fail`(기본) · `create` |
| `valueType` | | `label` · `text` · `number` · `date` · `link` · `image` |
| `allowMultiple` | | 만들 태그에 값을 여러 개 붙일 수 있는지(기본 거짓) |
| `color` | | 만들 태그의 표시 색상(ARGB 정수) |
| `nodeType` | | `path`를 무엇으로 읽을지: `file`(기본) · `directory` · `keyword` |
| `valueNodeType` | | `link` 값을 무엇으로 읽을지(같은 세 값, 기본 `file`) |
| `missingKeyword` | | 지목한 키워드가 없을 때: `fail`(기본) · `create` |
| `missingLink` | | `link` 값의 대상을 찾지 못했을 때: `fail`(기본) · `keep` |

- `op`
  - `add` — 값을 부여합니다. 다중값 태그면 기존 값을 남긴 채 하나 더 붙습니다.
  - `replace` — 그 태그의 기존 부여를 모두 걷어내고 이 값 하나로 둡니다.
  - `remove` — `value`를 주면 그 값의 부여만, 주지 않으면 그 태그를 통째로 뗍니다.
- `missing: create`는 **`valueType`이 반드시 있어야** 합니다(기본값을 두면 오타 하나가
  유령 태그를 만듭니다). `allowMultiple`·`color`는 **적으면 그대로** 쓰이고, 적지 않으면
  단일값·색 없음으로 만들어집니다. 여러 값을 붙일 태그라면 `allowMultiple: true`를 꼭
  적으세요 — 단일값 태그는 재부여가 **갱신**이라 값이 마지막 하나만 남습니다.
- 태그가 **이미 있으면** `valueType`이 다를 때만 실패하고, `allowMultiple`·`color`는
  무시합니다(이미 있는 태그의 성질을 외부에서 바꾸지 않습니다).
- `op`·`missing`·`valueType`·`nodeType`·`valueNodeType`·`missingKeyword`·`missingLink`에
  **모르는 이름**을 쓰면 기본값으로 눕히지 않고 형식 오류로 처리합니다(오타 난 `remove`가
  조용히 부여가 되지 않도록).
- 앱이 해석하지 않는 키(예: 외부 앱의 요청 식별자)를 함께 넣어도 됩니다. 실패로 되돌아올
  때 그대로 보존됩니다.

#### 값 유형별 `value`

| 유형 | `value`에 쓰는 것 |
| --- | --- |
| `label` | 없음(값 없는 태그) |
| `text` | 문자열 그대로 |
| `number` | 숫자로 읽히는 문자열 |
| `date` | ISO-8601 문자열(날짜 부분만 저장됩니다) |
| `link` | **대상 항목의 관리 폴더 기준 상대 경로**(앱이 내부 식별자로 바꿉니다) |
| `image` | **이미지 파일의 경로** — 절대 경로면 그 파일을, **상대 경로면 요청함 폴더 기준**으로 찾아 캐시에 등록합니다 |

`link`·`image`를 외부 앱이 내부 식별자나 캐시 키로 지정할 수는 없습니다 — 그 값들은
앱 내부 표현이라 공개하지 않습니다. 그래서 **`image`의 제거는 언제나 태그 통째로**입니다
(지울 값을 지목할 수단이 없고, 값을 넘기면 오히려 새 이미지를 등록하게 됩니다).

#### 대상이 아직 없는 링크 (`missingLink`)

`link` 값이 가리키는 항목이 관리 폴더에 없으면 기본은 **실패**입니다(오타 난 경로가 조용히
값으로 굳지 않게).

`missingLink: keep`을 주면 실패시키는 대신 **적어 보낸 원문을 값으로 남기고 '미해결 링크'로
표시**합니다. 앱은 그 항목에 시스템 태그 **`미해결 링크`**를 붙이므로, 사용자가 필터에서
그것만 모아 링크 칩을 더블클릭해 다시 연결하거나 지울 수 있습니다.

태그 묶음을 다른 관리 폴더로 옮길 때 쓰라고 둔 값입니다 — 링크 대상까지 함께 옮기지
못했더라도 값을 버리지 않아, 나중에 이어 붙일 여지가 남습니다.

```json
{ "path": "신작/01.png", "tag": "작가",
  "value": "홍길동", "valueNodeType": "keyword", "missingLink": "keep" }
```

`missingKeyword`와 자리가 겹치지 않습니다. 키워드 링크에서는 **생성이 먼저** 판정되고
(`missingKeyword: create`면 만들어 걸립니다), 만들지 않기로 한 뒤에 이 설정이 "그래도 값을
남길지"를 정합니다. 파일 링크에는 생성이라는 선택지가 없어 이 설정만 걸립니다.

#### 키워드를 가리키기

**키워드**는 디스크에 파일로 남지 않고 태그 저장소 안에만 있는 항목입니다. **이름 하나가
전부**이고, 작가의 국적·계정 같은 부연 정보는 그 키워드에 **태그로** 붙입니다(그래야 검색·
필터에 걸립니다). 파일이 아니라 이름으로 지목하므로, 경로와 헷갈리지 않도록 판별 필드를
함께 적습니다.

- `nodeType: keyword` — `path`를 **키워드 이름**으로 읽습니다. 이름이 같은 파일이 있어도
  서로를 밀어내지 않습니다(키 공간이 다릅니다).
- `valueNodeType: keyword` — `link` 값을 키워드 이름으로 읽습니다. **`nodeType`과 따로 두는
  이유**는 둘이 대개 다르기 때문입니다 — 그림 **파일**에 작가 **키워드**를 링크로 거는 것이
  주 용도입니다.
- `file`과 `directory`는 앱이 구분하지 않습니다(둘 다 경로로 찾습니다). 뜻을 적어 두고
  싶을 때 골라 쓰세요.
- 키워드 이름에는 **경로 구분자를 쓸 수 없습니다.** `a/작가` 같은 값은 경로처럼 접어 받지
  않고 형식 오류로 되돌아옵니다.
- 지목한 키워드가 없으면 **곧바로 실패**입니다. 파일과 달리 보류가 없습니다 — 키워드는 앱이
  만들어야만 존재하므로 기다린다고 나타나지 않습니다.
- `missingKeyword: create`를 주면 그 이름의 키워드를 만들어 진행합니다. 이름이 전부이므로
  만들 때 더 줄 것은 없습니다. 이 설정은 `path`와 `link` 값 **양쪽에 함께** 적용됩니다.
- 키워드도 **시스템 태그는 바꿀 수 없습니다** — 특히 이름 태그가 열리면 요청함이 키워드의
  이름을 바꾸는 통로가 됩니다(파일에서 rename 통로를 막은 것과 같은 이유).

```json
{ "path": "신작/01.png", "tag": "작가",
  "value": "홍길동", "valueNodeType": "keyword", "missingKeyword": "create" }
```

```json
{ "path": "홍길동", "nodeType": "keyword", "tag": "국적", "value": "한국" }
```

위 둘을 함께 넣으면 그림에 작가 링크가 걸리고, 그 작가 키워드에 국적이 붙습니다.

#### 예시: 다운로드한 이미지에 태그까지 붙이기

관리 폴더가 `D:\만화`이고, 외부 앱이 `01.png`를 받아 `D:\만화\신작\`에 저장한 상황입니다.

**1) 파일을 먼저 저장합니다.**

```
D:\만화\
├─ .filetagger\            ← 앱이 만든 폴더
│  ├─ filetagger.sqlite
│  ├─ view.json
│  └─ queue\               ← 요청을 넣는 자리
└─ 신작\
   └─ 01.png               ← 방금 저장한 파일
```

**2) 요청 파일을 쓰고, 다 쓴 뒤 `.json`이 되도록 옮깁니다.**

```
D:\만화\.filetagger\queue\a1b2c3.json.tmp ← 여기에 쓰고
D:\만화\.filetagger\queue\a1b2c3.json     ← 다 쓴 뒤 이 이름으로 옮긴다
```

파일 이름은 자유이고 요청함 안에서 겹치지만 않으면 됩니다. **확장자는 `.json`**이어야
요청으로 읽히므로, 쓰는 중인 임시 파일은 같은 폴더에 두어도 안전합니다.

**3) 파일 내용**은 UTF-8 JSON 객체 하나입니다. `path`는 **관리 폴더 루트 기준 상대 경로**
(`D:\만화`를 뺀 나머지)이고, 구분자는 `/`·`\` 어느 쪽이든 됩니다.

```json
{
  "path": "신작/01.png",
  "tag": "작가",
  "value": "홍길동",
  "missing": "create",
  "valueType": "text"
}
```

**4) 앱이 하는 일**

- 앱이 **켜져 있고 `D:\만화`를 열어 두었다면** 곧바로(파일이 놓인 것을 감지해) 처리합니다.
  **꺼져 있었다면** 다음에 그 폴더를 열 때, 스캔이 끝난 직후에 처리합니다.
- `신작/01.png`를 인덱스에서 찾고, `작가` 태그가 없으므로 텍스트 값 유형으로 만든 뒤
  값 `홍길동`을 부여합니다.
- 성공했으므로 `queue\a1b2c3.json`을 **지웁니다.** 요청함이 비면 아무 흔적도 남지 않습니다.
- 데스크톱 상태표시줄에 "외부 적용 1"이 조용히 표시됩니다(다이얼로그·알림은 없습니다).

**실패했다면** 파일은 지워지지 않고 그 자리에 남아, 내용에 `failure`가 덧붙습니다.
예를 들어 `missing`을 적지 않아 `작가` 태그를 만들지 못했다면:

```json
{
  "path": "신작/01.png",
  "tag": "작가",
  "value": "홍길동",
  "failure": {
    "reason": "tagMissing",
    "at": "2026-08-01T12:34:56.000",
    "message": "그 이름의 태그가 없습니다."
  }
}
```

외부 앱은 자기가 만든 경로(`queue\a1b2c3.json`)를 그대로 다시 읽어 결과를 알 수 있습니다.
**파일이 없으면 성공, 있으면 아직 처리 전이거나 `failure`에 사유가 적혀 있습니다.**

#### 그 밖의 요청 예시

이미 있는 라벨 태그를 붙이기(값 없음):

```json
{ "path": "신작/01.png", "tag": "읽음" }
```

기존 값을 모두 걷어내고 이 값 하나로 두기:

```json
{ "path": "신작/01.png", "tag": "평점", "op": "replace", "value": 5 }
```

다중값 태그에서 값 하나만 떼기(`value`를 빼면 그 태그를 통째로 뗍니다):

```json
{ "path": "신작/01.png", "tag": "장르", "op": "remove", "value": "판타지" }
```

이미지 파일을 폴더의 표지 썸네일로 걸기:

```json
{
  "path": "신작",
  "tag": "표지",
  "value": "C:/Downloads/cover.jpg",
  "missing": "create",
  "valueType": "image"
}
```

이미지를 요청 파일 **옆에 함께 둔 경우**는 상대 경로로 가리킵니다(요청함 폴더 기준).
파일 몇 개를 통째로 옮기는 것만으로 이관이 되도록 하기 위한 자리입니다.

```json
{ "path": "신작", "tag": "표지", "value": "cover.jpg",
  "missing": "create", "valueType": "image" }
```

관리 폴더 **안**의 다른 항목을 가리키기(값은 그 항목의 상대 경로):

```json
{ "path": "신작/01.png", "tag": "다음 화", "value": "신작/02.png" }
```

#### 실패 사유와 재시도

실패 표식은 **원래 쓴 내용을 그대로 둔 채** `failure`만 덧붙습니다. 앱이 해석하지 않는
키(요청 식별자 등)를 함께 넣어 두었다면 그것도 남아 있어, 어느 요청의 결과인지 짚을 수
있습니다. `reason`은 기계적으로 분기하라고 두는 값이고, `message`는 사람이 읽는 세부입니다.

| `reason` | 뜻 |
| --- | --- |
| `malformed` | 요청으로 읽지 못함(JSON 아님, 필수 필드 없음, 모르는 이름) |
| `targetMissing` | `path`가 디스크에 없음 |
| `targetNotManaged` | 디스크엔 있으나 관리 범위 밖이라 인덱싱되지 않는 자리 |
| `systemTag` | 시스템 태그는 외부에서 바꿀 수 없음 |
| `tagMissing` | 그 이름의 태그가 없고 `missing: create`도 아님 |
| `valueTypeMissing` | 태그를 만들어야 하는데 `valueType`이 없음 |
| `valueTypeMismatch` | 이미 있는 태그의 값 유형이 다름 |
| `invalidValue` | 값을 그 유형으로 읽지 못함(숫자·날짜 형식, 없는 이미지 파일, 없는 링크 대상) |

- **`failure`가 붙은 항목은 이후 패스에서 건너뜁니다** — 같은 실패를 앱을 켤 때마다
  되풀이하지 않기 위해서입니다. **재시도하려면 `failure` 없이 같은 파일을 덮어쓰세요.**
- 실패 항목이 오래되거나 너무 많이 쌓이면 앱이 정리합니다. 아직 처리되지 않은(표식 없는)
  항목은 나이만으로 지우지 않습니다.
- 데스크톱에서는 상태표시줄에 마지막으로 적용·실패한 건수가 조용히 표시됩니다.

#### 알아 둘 규칙

- **대상은 경로로만 지목합니다.** 크기·해시 같은 대조 필드가 없으므로, 지워진 파일 자리에
  같은 이름의 새 파일이 생기면 그 파일에 태그가 붙습니다.
- **파일을 먼저 디스크에 쓰고 요청함에 넣으세요.** 이 순서를 전제로, 대상이 디스크에 없으면
  기다리지 않고 즉시 실패로 기록합니다. 디스크에는 있는데 앱이 아직 스캔하지 못했을 뿐이면
  실패로 적지 않고 다음 패스로 넘깁니다.
- **시스템 태그**(크기·수정 시각·파일 이름 등)는 대상이 아닙니다.
- **같은 명령을 다시 넣어도 결과는 같습니다** — 재시도가 다중값 태그에 중복을 쌓지 않습니다.
- 하위 폴더가 자체 `.filetagger/`를 가진 경우, **그 요청함은 그 폴더를 앱에서 열 때 처리**됩니다.
  상위에서 흡수하면 대기 중인 항목만 상위 요청함으로 옮겨집니다.
- 어떤 파일에 어떤 태그를 붙일지 **판단하는 규칙은 앱에 두지 않습니다.** 조건을 보고 요청을
  만드는 일은 외부 앱의 몫입니다.

### 태그 내보내기

앱이 **같은 형식으로 내보내기도** 합니다. 목록에서 항목을 고르고 '파일 → 태그 내보내기…'
(또는 우클릭)를 누르면, 고른 항목의 태그가 요청 파일 **하나**로 저장됩니다.

받는 쪽에는 **가져오기 기능이 따로 없습니다** — 내보낸 파일을 그 관리 폴더의
`.filetagger/queue/`에 넣기만 하면 요청함이 그대로 읽어 적용합니다.

- 내보낼 태그는 **고른 항목이 실제로 가진 태그**만 후보로 뜨고, 기본은 전체 선택입니다.
- **태그값 포함**을 끄면 태그만 붙고 값은 비어 갑니다.
- **이미지 파일 포함**을 켜면 커스텀 썸네일 이미지를 요청 파일 **옆에** 함께 씁니다.
  두 파일을 같이 옮겨야 이미지가 붙습니다(요청함이 상대 경로를 자기 폴더 기준으로 찾습니다).
- 태그가 없으면 만들도록 값 유형·다중 허용·색을 함께 싣습니다.
- 링크 값은 대상의 경로(키워드는 이름)로 풀어 나가고 `missingLink: keep`이 붙습니다 —
  **대상을 함께 옮기지 않았어도 값이 남아**, 받는 쪽에서 '미해결 링크'로 기다립니다.
- 시스템 태그는 담지 않습니다(자동 파생이라 요청함이 거부합니다).

## 내려받기 / 빌드

**Linux**는 릴리즈 페이지에서 포터블 tar.gz를 내려받아 압축만 풀면 됩니다.

**Windows 실행 파일은 릴리즈에 싣지 않습니다.** 코드 서명이 없는 실행 파일을 웹에서
내려받으면 Windows가 SmartScreen 경고를 띄우기 때문입니다. 직접 빌드하면 그 경고 없이
릴리즈와 같은 포터블판을 얻을 수 있고, 아래 절차가 그 방법입니다. Microsoft Store
배포는 준비 중이며, 나오면 그쪽이 더 간편한 길이 됩니다.

> **Flutter SDK 없이 CMake만으로는 빌드할 수 없습니다.** `windows/flutter/CMakeLists.txt`가
> Flutter 툴이 만들어 내는 설정 파일을 읽고, 빌드 도중 다시 Flutter 툴을 호출해 Dart
> 코드를 컴파일하기 때문입니다. 다만 **Visual Studio는 전체 설치 없이 Build Tools만으로**
> 됩니다.

### Windows에서 빌드하기

**1단계 — C++ 빌드 도구 설치**

Visual Studio IDE 전체는 필요 없습니다. **관리자 권한 PowerShell**에서:

```powershell
winget install --id Microsoft.VisualStudio.2022.BuildTools --exact --source winget --override "--passive --wait --add Microsoft.VisualStudio.Workload.VCTools --add Microsoft.VisualStudio.Component.VC.Tools.x86.x64 --add Microsoft.VisualStudio.Component.VC.CMake.Project"
```

설치 관리자 화면에서 직접 고른다면 워크로드 하나와 그 안의 구성 요소 둘입니다. Build
Tools 설치 관리자에서는 **"C++ 빌드 도구"**, Visual Studio IDE 설치 관리자에서는
**"C++를 사용한 데스크톱 개발"** 워크로드이고, 오른쪽 구성 요소 목록에서 **MSVC 빌드
도구**와 **Windows용 C++ CMake 도구**가 켜져 있어야 합니다(기본으로 켜져 있습니다).

**2단계 — Flutter SDK 설치**

[Flutter 공식 설치 안내](https://docs.flutter.dev/get-started/install/windows/desktop)에서
SDK 압축 파일을 받아 원하는 위치에 풀고, 그 안의 `bin` 폴더를 환경 변수 `Path`에
추가합니다. **새 PowerShell 창을 연 뒤** 아래로 확인합니다.

```powershell
flutter doctor
```

`Visual Studio - develop Windows apps` 줄에 체크가 뜨면 1단계가 제대로 된 것입니다.
Android 관련 줄에 경고가 남아 있어도 이 앱을 빌드하는 데는 상관없습니다.

**3단계 — 빌드**

저장소를 받아 그 폴더에서:

```powershell
flutter pub get
flutter build windows --release
```

**추가 인자는 필요 없습니다.** 이렇게 빌드하면 릴리즈와 같은 포터블판(설정을 실행 파일
옆에 두는 형태)이 나옵니다. 버전도 따로 지정할 필요가 없습니다 — Flutter 빌드가
`pubspec.yaml`의 버전을 실행 파일에 새기고 앱이 그것을 되읽어, 정보 창에 보이고
업데이트 확인도 그 값으로 최신 릴리즈와 견줍니다.

**4단계 — 산출물**

```
build\windows\x64\runner\Release\
```

이 폴더가 통째로 한 벌입니다. `filetagger.exe` 하나만 떼어 내면 실행되지 않으므로
**폴더째** 원하는 위치로 옮겨서 쓰세요.

### Linux에서 빌드하기

C++ 도구와 GTK 개발 헤더가 필요합니다(Debian·Ubuntu 계열 기준).

```bash
sudo apt-get install -y clang cmake ninja-build pkg-config libgtk-3-dev liblzma-dev libstdc++-12-dev
flutter pub get
flutter build linux --release
```

산출물은 `build/linux/x64/release/bundle/`에 나옵니다.

### 개발용 실행 · 코드 생성

```bash
flutter run -d windows        # 또는 -d linux
```

개발 실행도 포터블로 잡히므로 **전역 설정이 빌드 폴더 안에 남고, 빌드를 지우면 함께
사라집니다.** 첫 실행 상태를 다시 보고 싶을 때 그 파일만 지우면 됩니다.

생성 파일(`*.g.dart`)은 저장소에 함께 커밋되어 있으므로 **빌드 전에 따로 돌릴 필요가
없습니다.** DB 스키마 등 생성 대상을 고쳤을 때만 다시 만듭니다.

```bash
dart run build_runner build   # 코드 생성 (Drift)
```
